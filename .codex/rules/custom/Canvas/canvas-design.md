# Canvas 작성 규칙 (Obsidian Advanced Canvas)

> Obsidian `.canvas` 파일 (JSON Canvas spec + Advanced Canvas 확장) 작성 시 적용.
> 도메인: 구조도, 시스템 도식, 데이터 흐름, 영역 매핑 등 시각 자료 작성.

## 1. 적용 범위

- 모든 `.canvas` 파일 직접 생성 / 편집 작업
- 트리거: "캔버스 만들어", "구조도 그려", "advanced canvas", "Obsidian Canvas", ".canvas" 파일 작업
- 시안용 임시 캔버스 외에도 정식 spec/plan 첨부 캔버스 모두 포함

## 0. 최상위 원칙 — 텍스트 가시성 > 정렬

캔버스 시각화의 기본은 **읽힘**. 우선순위:

### 0.1 P1 — 텍스트 가시성 (가장 우선)

다음 세 종류의 텍스트가 모두 가려지지 않게 적절한 공간 확보:

1. **노드 내부 텍스트** — 노드 width/height 가 텍스트 + padding 보다 충분히 커서 스크롤바·의도 안 한 wrap 없음
2. **그룹 박스 제목 (라벨)** — group 상단의 라벨 영역 (50~80px) 에 자식 노드가 침범하지 않음. 즉 모든 자식 노드의 `top ≥ group.y + 60`
3. **edge 라벨** — 노드 간 gap 이 라벨 폭의 약 2~3배 이상. 라벨이 노드 안·다른 edge·다른 group 라벨에 가려지지 않음

### 0.2 P2 — 정렬·간격 일관성 (P1 만족 후)

- 같은 row 안 노드는 동일 y
- 그룹 간 row gap 일관
- 노드 간 column 정렬 (가능한 한)
- 색상·테두리 통일

### 0.3 충돌 시 P1 우선

P1 과 P2 가 충돌하면 **P1 (가시성) 우선**. 예:

- 한 row 안 한 노드가 텍스트 길어서 width 더 필요 → 그 노드만 더 키움. 같은 row 의 다른 노드 width 일관성 깨져도 OK
- 한 group 의 라벨이 길어서 자식 top 마진 + 60 만으로 부족 → 80~100 으로 키움. 다른 group 마진과 다르더라도 OK
- row gap 일관 80 인데 한 곳의 edge label 이 김 → 그 row gap 만 150 으로. 다른 gap 과 달라도 OK

§ 2 (노드 크기) · § 3 (간격) · § 6 (그룹 박스) 의 세부 룰은 이 원칙을 만족시키기 위한 수단. **세부 룰이 P1 과 충돌하면 P1 우선**.

### 0.4 검증 시점

- AI 시드 작성 직후 — 자식 좌표 vs group 좌표 + 노드 간 gap vs 라벨 폭 시뮬레이션
- **AI 자체 시각 캡쳐 검증 (R127 도입)** — PowerShell + System.Drawing 으로 화면 캡쐐, Read 도구로 PNG 분석. 사용자에게 묻기 전에 자체 확인 가능.
- 사용자 시각 확인 후 — 가려진 텍스트 있으면 즉시 보강 (정렬 양보)

### 0.5 AI 자체 캡쳐·검증 흐름 (R127)

Obsidian 캔버스 가 사용자 모니터에 보일 때 AI 가 직접 검증:

```powershell

$g.CopyFromScreen(0, 0, 0, 0, (New-Object System.Drawing.Size(1920, 1080)))
$bitmap.Save($temp)

# 2. 부분 crop + 2x 확대 (Group/edge 영역 자세히)
$rect = New-Object System.Drawing.Rectangle($x, $y, $w, $h)
$crop = New-Object System.Drawing.Bitmap([int]($w*2), [int]($h*2))
# DrawImage with HighQualityBicubic interpolation
```

그 다음 Read 도구로 PNG 분석 (claude 멀티모달). 노드 텍스트 가림 / edge label 위치 / 그룹 라벨 침범 시각 검증.

**전제 조건**: Obsidian 활성화 + 캔버스 보이는 모니터 + 적절한 줌 레벨.

## 2. 노드 크기 — 시각 검증 우선

### 2.1 원칙

- **정확한 픽셀 공식은 신뢰하지 않음** — 폰트·테마·플랫폼·줌 레벨에 따라 줄 높이·문자 폭이 다름.
- **시각 검증 + 사용자 조정 후 패턴 학습** 이 핵심.
- AI 가 시드 생성 시는 **대략 범위**로 잡고, 사용자가 직접 보고 조정하게 한다.
- 한 세션 안에서 사용자가 어떤 노드 크기를 조정하면, **그 패턴**을 같은 캔버스의 다른 노드에 적용한다 (절대값 외운 휴리스틱 무시).

### 2.2 시드 생성용 대략 가이드 (참고)

높이 시드 — **줄 종류 분류 합산**:

| 줄 종류 | 1줄 height (시드) |
|---------|----------------|
| 제목 줄 (`#`, `##` 등) | 28~32 |
| 일반 텍스트 줄 | 22~26 |
| bullet 줄 (`- ...`, `* ...`) | 28~32 ← 들여쓰기 + bullet 마크 차지 |
| 빈 줄 / 구분 줄 | 12~16 |
| padding (상하 합) | 30~40 |

```
height ≈ Σ(줄 종류별 height) + padding
```

예시:

- "제목 + 일반 2줄" (예: note, filename) → 30 + 24×2 + 30 = **108** (시드 110~140)
- "제목 + bullet 4줄" (예: body) → 30 + 30×4 + 30 = **180**
- "제목 + 일반 2 + bullet 4" (예: frontmatter) → 30 + 24×2 + 30×4 + 30 = **228** (안전마진 +30 → 260)
- "제목 + bullet 3" (예: pascalcase) → 30 + 30×3 + 30 = **150** (시드 150~170)

**bullet 비율이 높은 노드는 줄 수가 같아도 일반 텍스트보다 height 가 더 큼**. 시드 작성 시 줄 종류별로 합산.

빠른 참고 표 (혼합 줄 가정, 단순 평균):

| 총 줄수 | bullet 위주 | 일반 위주 |
|------|----------|---------|
| 3 | 150~180 | 110~140 |
| 4 | 180~210 | 130~160 |
| 5 | 210~240 | 160~190 |
| 6+ | 240~280 | 200~230 |

폭 시드는 **언어 환경에 따라 분리** — 한국 사용자는 한글 + 영문 혼합이 흔하므로 둘 다 명시.

#### A. 영문 전용 노드 (한글 없음)

- 짧은 한 줄 (10자 이내): 180~240
- 일반 정보 노드 (20~30자): 260~340
- 위키링크/긴 영문 토큰 포함: 토큰 길이 × 약 10 + 60 여유
- 페이지 라벨·목록 한 줄에 펼치는 노드: 400~500+

영문 1자 시각 폭 추정: **8~11px** (테마·폰트에 따라). 시드 = 가장 긴 줄 자 수 × 10 + 50.

#### B. 한글 + 영문 혼합 노드 (한국 사용자 기본)

- 짧은 한 줄 (한글 5자 이내): 200~260
- 일반 정보 노드 (한글 + 영문 mix 한 줄 ~15자): 260~360
- 위키링크 포함: 토큰 길이 × 10 + 한글 폭 + 60
- 페이지 라벨·목록 한 줄에 펼치는 노드: 400~500+

한글 1자 시각 폭 추정: **14~18px** (영문의 약 2배). 시드 = (한글 자 수 × 16) + (영문 자 수 × 10) + 50.

**위 두 표는 시드용 출발값**. 사용자 환경에 따라 ±30% 이상 차이날 수 있음. 둘 중 노드의 가장 긴 줄 특성에 맞춰 선택.

### 2.3 줄바꿈 금지 토큰

다음 토큰은 한 줄 안에 들어가야 시각상 자연스러움 (wrap 되면 가독성·식별 떨어짐):

- 위키링크 `[[...]]`
- 코드 ``` ` ``` 인라인
- URL `https://...`
- 명령어 한 줄 `node cli.js sync` 등 식별성 있는 문자열

이 토큰이 있을 땐 시드 width 를 토큰 폭 기준 넉넉히 (토큰 char × 약 9~12px + 여백 60). 정확한 값은 사용자 캔버스에서 확인 후 조정.

### 2.4 검증 — 스크롤바·wrap·여백

Obsidian Canvas text 노드는 크기 부족 시 자동 스크롤바 생성. 캔버스 열어 시각 확인:

- **가로 스크롤바** → width 늘림
- **세로 스크롤바** → height 늘림
- **의도 안 한 wrap** → width 늘림 또는 줄바꿈 명시
- **노드 안에 큰 빈 공간** → 크기 줄임 (선택 — 시각 일관성 우선 시 그대로)
- 스크롤바·과한 wrap 없고 적정 여백 → OK

### 2.5 한 캔버스 안 패턴 학습 (강제)

§ 2.2 시드는 **보편 가이드라인**이지 사용자 표준이 아니다. 사용자는 캔버스마다 보고 직접 조정한다.

사용자가 한 캔버스 안에서 노드 크기를 조정한 직후:

1. 조정된 노드의 텍스트 줄 수·문자 종류 (한글/영문/위키링크) 와 적용된 width/height 추출
2. **같은 캔버스 안** 비슷한 텍스트 특성의 다른 노드에 비례 패턴 적용 (절대값 X, **상대 비율**)
3. 사용자가 만진 노드 좌표·크기는 절대 임의 변경 금지

→ 한 캔버스 안에서만 유효한 학습. 다른 캔버스로 절대값 복사 X (캔버스마다 폰트·줌·콘텐츠 다름).

### 2.6 헤딩 폰트 wrap 처리 (R127)

마크다운 헤딩 (`#`, `##`) 텍스트는 본문 폰트보다 **1.3~1.8배 큼**. 같은 char 수라도 시각 폭 더 큼.

- 시드 width 산정 시 헤딩 줄을 **본문 폭 × 1.5** 로 계산
- 헤딩이 wrap 되면 width 더 키우거나 **wrap 받아들이고 height 추가** (한 줄 → 2줄)
- 헤딩 width 무한정 키우면 캔버스 전체 폭 비대 → 트레이드오프
- 일반적으로 **height 양보가 width 양보보다 시각상 자연스러움**

### 2.7 단위 스냅 (Obsidian Canvas 특성)

Obsidian Canvas 의 노드 크기 조정 시 마우스 드래그는 일정 단위 (대략 10~20px) 로 **snap**. AI 시드 값이 정확히 일치 안 해도 사용자 마우스 조정 시 자동 정렬됨.

- AI 시드는 대략 (예: width 380) 으로 두고 사용자가 조정
- 정확한 픽셀 단위 (예: width 384) 까지 맞추려 노력 X — 토큰 낭비

## 3. 노드 간 간격 — 라벨 가독성 기준

### 3.1 핵심 원칙

edge 라벨은 화살표의 **중앙에 떠 있는 작은 텍스트**다. 양쪽 노드 사이 빈 공간 (gap) 이 충분하지 않으면:

- 라벨이 한쪽 노드 안에 가려져 안 보임
- 라벨이 다른 edge·노드 위에 겹쳐 읽기 어려움
- 화살표가 너무 짧아 시각상 답답함

**가장 안전한 기준**: gap 이 라벨 시각 폭의 **약 2~3배** (라벨 양쪽에 자기 폭만큼 여유). 라벨이 짧으면 절대 최소값 (100~120px) 도 적용.

### 3.1.1 라벨 종류별 분기 (사용자 의도)

| 라벨 종류 | 예시 | gap |
|---------|------|-----|
| **1자 기호** (+, →, ↓, ✓) | `+`, `→` | **30~60** (좁아도 시각 OK) |
| **2~3자 한글** | `자동`, `집계`, `소속` | **100~140** |
| **4~5자 한글 또는 영문 단어** | `편집 후`, `sync`, `fetch` | **140~220** |
| **6자+ 한글 또는 영문 어구** | `BAD=0 → 빌드`, `Domain Preset 만` | **220~350** |
| **명령어 한 줄** | `BAD=0 → index build -i` | **350~500** |

**핵심**: 1자 기호 (+/→) 만 gap 좁힘 OK. 텍스트 라벨은 노드 사이 빈 공간이 라벨 폭의 2~3배 보장 필수.

### 3.2 시드용 대략 가이드

라벨 폭을 정확히 계산할 수 없으니 **라벨의 글자 수와 종류** 기반 휴리스틱. 한국 사용자 환경 = 한글 + 영문 혼합이 흔하므로 두 케이스 분리.

#### A. 영문 전용 라벨

| 라벨 자 수 | 라벨 시각 폭 (추정) | 시드 gap |
|----------|------------------|---------|
| 1~3 (`+`, `→`, `OK`) | 8~30 | **100~140** |
| 4~7 (단어 1개, "sync", "fetch") | 32~70 | **150~220** |
| 8~14 (단어 2개, "agents-sync", "deploy-dist") | 70~140 | **220~320** |
| 15~25 (영문 어구) | 140~250 | **320~450** |
| 25+ (명령어 한 줄, "BAD=0 → index build -i") | 200~350 | **450~600** |

영문 1자 시각 폭 추정: **8~11px**. 시드 = 자 수 × 9.

#### B. 한글 + 영문 혼합 라벨 (한국 사용자 기본)

| 라벨 종류 | 라벨 시각 폭 (추정) | 시드 gap |
|---------|------------------|---------|
| 매우 짧음 (1~2자 한글, "+", "→") | 16~32 | **100~140** |
| 짧음 (3~5자 한글, "편집 후", "룰 라우팅") | 48~80 | **150~220** |
| 중간 (5~8자 한글 또는 한글+영문 혼합 한 줄) | 80~140 | **220~320** |
| 김 (10자+ 한글 또는 "Claude ↔ Codex" 같은 mix) | 140~220 | **320~450** |
| 매우 김 (15자+ 또는 명령어 한 줄) | 200~350 | **450~600** |

라벨 폭 추정: **한글 자 수 × 16 + 영문 자 수 × 8 + 기호 × 6**. ±50% 오차 가능 — 시드용.

#### 케이스 선택

라벨 안에 한글이 1자라도 있으면 B 적용. 영문/기호만이면 A 적용.

### 3.3 그룹 박스 내부 vs 외부

- **그룹 박스 내부의 노드 간 gap**: 위 시드 그대로 적용 (그룹은 외곽 라벨만 추가)
- **그룹 박스 간 간격 (그룹↔그룹)**: 더 후하게. 그룹 외곽선 + 그룹 라벨 표시 공간 포함해서 그룹 간 80~150px 빈 공간

### 3.4 세로 (row 간) 간격

같은 row 안 edge 는 가로. row 간 edge (예: data → viz) 는 세로 또는 대각선:

- 위 row 의 max bottom + 아래 row 의 min top 사이 **gap ≥ 60~120**
- edge 라벨이 row 사이 공간에 들어가면 그 라벨 폭만큼 추가 (가로 라벨이라도 row 간 세로 공간 침범)
- 세로 edge 가 다른 노드 위 통과 시 시각상 부담 — row 간격 더 후하게 또는 edge 색·점선 으로 구분

### 3.5 검증 (시각 확인)

캔버스 열어 다음 점검:

- **라벨이 노드 안에 가려짐** → gap 늘림 (가장 흔한 문제)
- **라벨이 다른 edge·노드 위 겹침** → gap 늘림 또는 라벨 색·위치 조정
- **화살표 너무 길고 라벨 외로움** → gap 줄임 (선택, 시각 가독성 우선)
- **edge 가 다른 노드 통과** → 위치 재배치 또는 그룹 박스 추가로 영역 구분

### 3.6 한 캔버스 안 패턴 학습 (강제)

§ 3.2 시드는 보편 가이드라인. 사용자가 캔버스마다 직접 보고 조정한다.

사용자가 한 캔버스 안에서 노드 간 간격을 조정한 직후:

1. 조정된 노드 쌍의 (라벨 폭, gap, 마진) 추출
2. 같은 캔버스 안 비슷한 라벨 폭의 다른 edge 에 같은 비율 적용
3. **사용자가 조정한 라벨 위치·노드 위치 임의 변경 금지**

→ 한 캔버스 안에서만 유효한 학습. 다른 캔버스 만들 때는 다시 § 3.2 시드부터 시작.

## 4. 색상 매핑 (preset 1~6)

Obsidian Canvas 의 preset 색 (또는 hex). 영역별 의미 일관:

| Preset | 색 | 용도 |
|--------|-----|------|
| `"1"` | red | 안전·hooks·배포·경고 |
| `"2"` | orange | 통신·참고·외부 |
| `"3"` | yellow | Hub·인프라·코어 |
| `"4"` | green | 데이터·인덱싱·콘텐츠 |
| `"5"` | cyan | 룰·스킬·시각화·자동화 |
| `"6"` | purple | 진입점·spec·세션·메타 |

hex 색 (`"#rrggbb"`) 도 가능. 카테고리 색은 `presetColorByCategory()` 같은 viz 유틸과 정합 권장.

## 5. JSON 스키마 (Advanced Canvas)

```json
{
  "nodes": [
    {
      "id": "slug-or-hex16",
      "type": "text",
      "text": "## 제목\n본문 줄1\n본문 줄2",
      "x": -200,
      "y": -380,
      "width": 280,
      "height": 150,
      "color": "5"
    },
    {
      "id": "file-node-example",
      "type": "file",
      "file": "Vaults/.../path/to/note.md",
      "x": 400,
      "y": -380,
      "width": 600,
      "height": 400
    }
  ],
  "edges": [
    {
      "id": "edge-id",
      "fromNode": "source-id",
      "fromSide": "right",
      "toNode": "target-id",
      "toSide": "left",
      "label": "흐름",
      "color": "5"
    }
  ],
  "metadata": {
    "version": "1.0-1.0",
    "frontmatter": {}
  }
}
```

### 5.1 node 타입

- `text` — 마크다운 텍스트 (위키링크 OK)
- `file` — 볼트 노트 임베드 (큰 미리보기)
- `link` — URL 임베드
- `group` — 영역 묶음 라벨

### 5.2 edge 옵션

- `fromSide`/`toSide`: `top` / `right` / `bottom` / `left`
- `color`: preset 또는 hex
- `label`: edge 위 표시 텍스트
- `styleAttributes.pathfindingMethod`: `null` (직선) 또는 `"a-star"` (L자)
- `toFloating`: `false` (기본)

## 6. 레이아웃 원칙

1. **row 기반 가로 흐름** — 같은 row 안에서 동일 y 좌표, 왼쪽 → 오른쪽 데이터 흐름
2. **row 간 세로 흐름** — 위 row 결과가 아래 row 입력
3. **노드 겹침 금지** — 단 group 노드 내부는 허용 (그룹이 영역 표시 역할)
4. **그룹 색 일관** — 같은 영역은 같은 color preset
5. **시작점 노드는 좌상단** (예: 사용자 메시지, 진입점)
6. **종착점 노드는 우하단** (예: 배포, 결과물)

### 6.1 그룹 박스 (group node) 활용 — 권장

**여러 노드를 영역 단위로 묶을 때 group 노드 사용**. 그룹 박스가 영역 외곽선 + 라벨 역할.

```json
{
  "id": "group-row1",
  "type": "group",
  "label": "Row 1 — 영역 이름",
  "x": -870, "y": -600,
  "width": 2430, "height": 450,
  "color": "5"
}
```

**효과**:
- 같은 영역의 노드들이 시각적으로 묶임 (사용자 의미 파악 빠름)
- 그룹 박스 안에서는 노드 자유 배치 (겹침 없는 한)
- 그룹 박스 간 간격 = row 간 세로 흐름 표시
- Advanced Canvas 의 collapsible 기능 활용 가능 (그룹 접기)

**그룹 박스 좌표 결정 + 검증 (강제)**:

작성 절차:

1. 그룹에 포함될 모든 자식 노드 목록 확보
2. 자식 노드의 bounding box 계산:
   - `min_x = min(자식들의 x)`
   - `min_y = min(자식들의 y)`
   - `max_right = max(자식들의 x + width)`
   - `max_bottom = max(자식들의 y + height)`
3. group 박스 좌표:
   - `group.x = min_x - 30~50` (좌 padding)
   - `group.y = min_y - 50~80` (상 padding — 라벨 표시 공간)
   - `group.width = (max_right - min_x) + 60~100`
   - `group.height = (max_bottom - min_y) + 80~130`
4. **검증 (필수)** — 작성 후 다음 점검:
   - 모든 자식 `x ≥ group.x + 40` (좌 padding, R128 보강)
   - **모든 자식 `y ≥ group.y + 60` (상 padding — 라벨 영역 침범 방지)** ← § 0 원칙 직접 적용
   - 모든 자식 `x + width ≤ group.x + group.width - 40` (우 padding, R128)
   - 모든 자식 `y + height ≤ group.y + group.height - 40` (하 padding, R128)
5. 검증 실패 시 group 좌표 보정 또는 자식 노드 재배치
6. **라벨 영역 padding 은 가장 엄격** — 상단 60px 미만이면 group 라벨이 자식 노드에 가려질 위험

### 6.1.1 그룹 박스 "담는 형태" (R128, 사용자 패턴)

그룹 박스는 자식 노드에 **딱 붙는** 것이 아니라 **여유 있게 감싸는** 형태여야 시각적으로 "안에 담긴" 느낌. 사방 padding:

| 면 | 권장 padding |
|----|-----------|
| 상단 (라벨 영역) | **60~80** |
| 하단 | **40~50** |
| 좌측 | **40~50** |
| 우측 | **40~50** |

좌·우·하 30 으로 너무 좁으면 자식과 외각선이 닿아 보임 → 시각 답답함. 40+ 로 늘려서 "여유 공간" 표현.

P1 우선이라 padding 더 키워도 OK (시각 통일성 우선).

**가장 흔한 실수**: 자식 노드의 `y + height` 가 group bottom 을 넘어가는 경우 (자식이 그룹 박스 밖으로 튀어나옴). 시드 작성 시 자식의 max bottom 정확히 계산해서 group height 충분히 키워야.

**그룹 색상**: 안의 노드 색과 다르게 (시각 구분 강화) 또는 영역 대표 색 (의미 일관). 통상 안의 노드 색 중 가장 dominant 색.

**그룹 노드 우선 배치**: JSON `nodes` 배열에서 group 노드를 **맨 앞**에 두면 다른 노드가 위에 그려져 z-order 정상 (group 이 배경).

**그룹 간 간격**: 위 그룹의 bottom 과 아래 그룹의 top 사이 **최소 30~60px 빈 공간**. 그룹끼리 붙으면 외곽선 겹쳐서 시각 구분 약함.

## 7. 작성 → 검증 워크플로우 (강제, R127 보강)

1. **노드/엣지 목록 정리** — 사용자와 영역·요소 합의
2. **시드 캔버스 생성** — Write 으로 .canvas JSON 작성. § 2 / § 3 공식 적용
3. **시드 시뮬레이션 검증** — § 0.1 P1 항목 자체 점검:
   - 모든 자식 `y ≥ group.y + 60`
   - 모든 자식 `bottom ≤ group bottom - 30`
   - 각 row 간 edge label y 가 다음 group 라벨 영역 (`group.y ~ group.y + 40`) 밖
   - 같은 row 안 노드 간 gap 이 라벨 종류별 § 3.1.1 시드 이상
4. **Obsidian URI 열기** — `obsidian://open?vault=<볼트명>&file=<경로>` 자동 호출
5. **AI 자체 캡쳐 검증 (R127)** — § 0.5 PowerShell 캡쳐 + crop + Read 분석. 사용자에게 묻기 전 자체 점검.
6. **반복 조정** — 문제 노드의 width/height/x/y 수정 후 새로고침
7. **사용자 확인** — 최종 OK 받기

### 7.1 사용자 직접 조정한 노드 처리

사용자가 마우스로 직접 조정한 노드 (좌표 또는 크기) 는 **AI 가 임의 변경 금지**. 단:

- 사용자가 명시적으로 "다른 노드도 같은 패턴" 요청 시 → 사용자 패턴 분석 + 미수정 노드에만 적용
- 사용자 만진 노드는 좌표/크기 보존, 미수정 노드만 조정

### 7.2 토큰 절약 흐름 (R127)

- 시드 작성 직후 **자체 캡쳐 검증** → 사용자가 매번 보고할 필요 X
- 부분 crop + 2x 확대로 자세한 시각 분석 (텍스트 가림 / edge label 위치)
- 자체 발견한 문제만 수정 → 한 번에 정확히
- 사용자 의도 명확화 필요 시에만 묻기 (예: "+ 기호 vs 텍스트 라벨" 같은 선택)

## 8. 노드/엣지/그룹 ontology (R129, codex 5-20 리서치 흡수)

본 룰의 가장 큰 공백은 "어떤 노드를 그릴지 / 어떤 엣지를 그릴지" 분류 기준 부재. graph-ontology.md 의 ontology 를 압축 흡수.

### 8.1 노드 타입 15종

| 타입 | 한 줄 정의 | 색 권장 |
|------|---------|--------|
| **Actor** | 행동을 시작하는 주체 (사용자, 외부 SaaS, 에이전트) | 파랑 |
| **EntryPoint** | Actor 가 시스템과 만나는 접점 (API, UI, CLI) | 파랑 |
| **Rule** | 시스템 행동을 제약하는 규칙·정책 | 시안 |
| **Skill** | 입력→출력의 재사용 가능한 능력 단위 | 시안 |
| **Tool** | Skill/Agent 가 호출하는 외부 도구·API | 시안 |
| **DataStore** | 데이터가 영구 저장되는 장소 (DB, 파일 시스템) | 녹색 |
| **Index** | 빠른 조회용 인덱스 데이터 | 녹색 |
| **Vault** | Obsidian 볼트·지식 저장소 (도메인성 강한 DataStore) | 녹색 |
| **Agent** | 자율 판단·실행 주체 (LLM 기반 에이전트) | 보라 |
| **Process** | 시간 흐름이 있는 작업 (인덱싱, 빌드, 동기화) | 노랑 |
| **Verification** | 검증·테스트 지점 | 노랑 |
| **Output** | 결과물 (배포본, 리포트, 산출물) | 빨강 |
| **ExternalSystem** | 시스템 경계 밖 (외부 API, 외부 서비스) | 파랑 |
| **Risk / Constraint** | 위험·제약 사항 | 빨강 |
| **Decision** | 분기점·선택 (라우팅 결정 등) | 노랑 |

선택 기준: "이 노드의 역할이 무엇인가?" → 위 15종 중 가장 가까운 1개. 같은 타입은 같은 색.

### 8.2 엣지 타입 12종 (방향성 + 의미)

| 엣지 | 의미 | 예시 |
|------|------|------|
| **calls** | A 가 B 를 함수·API 호출 | Agent → Tool |
| **reads** | A 가 B 에서 데이터 읽음 | viz → master_index.json |
| **writes** | A 가 B 에 데이터 씀 | review → vault_index.json |
| **syncs** | A 와 B 가 양방향 동기화 | CoreHub ↔ Preset Hub |
| **validates** | A 가 B 를 검증 | review → 노트 편집 |
| **routes** | A 가 B 로 라우팅 결정 | skill router → 도메인 룰 |
| **owns** | A 가 B 를 소유·관리 | vault → owned_tags |
| **triggers** | A 가 B 를 시작·발동 | hook → agents-sync |
| **depends-on** | A 가 B 없이는 동작 X | viz → master_index |
| **derives-from** | A 가 B 에서 파생 | timeseries → master_index |
| **blocks** | A 가 B 를 차단·금지 | PreToolUse hook → NUL 리다이렉트 |
| **reports-to** | A 가 B 에 결과 보고 | session_handoff → 다음 세션 |

데이터 흐름 (reads/writes/syncs/derives-from) 과 제어 흐름 (calls/triggers/routes/blocks) 을 **다른 색/패턴**으로 구분 권장.

### 8.3 그룹 타입 7종

| 그룹 | 의미 |
|------|------|
| **Layer** | 추상화 계층 (UI, Service, Data) |
| **Domain** | 비즈니스 도메인 (Auth, Payment, Indexing) |
| **Runtime boundary** | 실행 환경 경계 (브라우저, 서버, CLI) |
| **Ownership boundary** | 책임 소유 경계 (팀, 사용자) |
| **Trust boundary** | 신뢰 경계 (내부/외부, 인증/비인증) |
| **Lifecycle phase** | 라이프사이클 단계 (Plan/Build/Test/Deploy) |
| **View / Concern** | 관점 별 묶음 (보안, 성능, 운영) |

그룹 라벨은 위 7종 중 하나의 의미를 명시 (예: "Layer — UI", "Domain — Indexing").

상세는 `reference/graph-ontology.md` (583줄) 참조.

## 9. 흔한 실패 8개 + 수정 지침 (codex rubric 압축)

## 10. 큰 캔버스 분리 기준 (codex 흡수)

한 캔버스에 노드 너무 많으면 가독성 X. 분리 기준:

### 10.1 노드/엣지 수 기준
- 노드 **40 초과**: 분리 후보
- 노드 **50 초과**: 강하게 분리 권장
- 엣지 **100 초과**: 분리 필수

### 10.2 관점 (View) 기준
- 컨텍스트 뷰 (외부와 경계)
- 구조 뷰 (내부 컴포넌트 관계)
- 데이터 흐름 뷰
- 제어 흐름 뷰
- 배포 뷰 (런타임 경계)
- 보안·리스크 뷰
- 라이프사이클 뷰

→ 각 view 1 canvas. file 노드로 cross-link.

### 10.3 경계 기준
- 시간 경계 (현재 시스템 vs 미래 계획)
- 책임 경계 (팀별·도메인별)
- 추상화 경계 (메타 캔버스 + 세부 캔버스)

상세는 `reference/canvas-layout.md` § 5 (레이아웃 패턴 7종) + § 6 (분리 기준) 참조.

## 11. 금지

- 빈 width/height (Obsidian 이 기본값 적용하지만 일관성 없음 — 항상 명시)
- 같은 id 중복 (JSON 파싱 안 됨)
- 좌표 정수 아닌 부동소수 (정수만 사용)
- node 끼리 겹침 (그룹 박스 제외)
- edge 의 fromSide/toSide 누락 (Obsidian 자동 추정하지만 일관성 X)
